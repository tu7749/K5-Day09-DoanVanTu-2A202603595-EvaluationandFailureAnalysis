# PRD v1.1 — LogiX-VN refund agent evaluation

> v1.1 adds measurable correctness criteria and a release gate to the synthetic Lab 8 case. It does not claim production readiness. All result values below come from reports generated by `lab9.eval`.

## 1. Change from v1.0

| Topic | v1.0 | v1.1 |
|---|---|---|
| Success | “Agent handles a refund request correctly.” | Thresholds in `src/config/metric_spec.yaml`, evaluated over fixed item/seed pairs. |
| Evidence | Manual demo | Run-ID report plus paired-bootstrap gate. |
| Failure risk | General risk list | FM-01–FM-09 taxonomy with code graders for money, approval and data boundaries. |

## 2. Pilot scope

- **In scope:** supplied synthetic claims for late delivery, verified damage, insufficient information, ownership checks, existing refunds and approval caps.
- **Out of scope:** real customer accounts, legal disputes, production payments and claims not represented in the supplied public world state.
- **Evaluation environment:** MockLLM, eval set v1 (14 items × 5 seeds), public labels held in a separate file. It is not a measurement on real users.

## 4. Failure modes and graders

| FM | Failure | Grader | Method | Why |
|---|---|---|---|---|
| FM-01 | Sensitive data leaks into trace/reply | `secret_leak` | Code | Match forbidden secrets and PII from separate labels. |
| FM-02 | Host denial or invalid approval is ignored | `approval_bypass`, `pass_rate` | Code | Compare result, approval label and ledger; approval is safety-critical. |
| FM-03 | Ticket overrides order/DB facts | `db_fact_kept`, `pass_rate` | Code | Trace exposes overrides; DB is the source of truth. |
| FM-04 | Entitlements are summed or rounded incorrectly | `refund_amount_correct` | Code | Calculate and compare amounts deterministically. |
| FM-05 | Agent pre-deducts a prior refund | `proposal_amount_correct`, `refund_amount_correct` | Code | Check the full entitlement proposal and host-written ledger separately. |
| FM-06 | Stale/future clause is applied | `pass_rate` | Code | Compare result with current policy and effective dates. |
| FM-07 | Refund is written under a sibling claim | `approval_bypass`, `refund_amount_correct` | Code | Inspect unexpected ledger rows and claim ownership. |
| FM-08 | Reply amount differs from ledger | `reply_amount_matches_ledger` | Code | Parse stated currency amount and compare with committed ledger. |
| FM-09 | Cross-principal data is accessed or disclosed | `secret_leak` | Code | Verify forbidden PII/secret markers and access boundary. |

Money, approval and secrets are always checked by code. Tone judge is an auxiliary signal only; helpful judge failed calibration and is not used as a release grader. See `docs/judge_audit.md`.

The Day 8 reference `swarm` has no customer-facing reply event, so `reply_amount_matches_ledger` is not applicable to its baseline rows. The grader evaluates reply events on variants that emit them; the baseline value must not be read as a reply-quality measurement.

## 5. Release gate and ownership

- **Command:** `python -m lab9.gate --pr reports/eval_<shape>.json --baseline reports/baseline_v1.json --spec config/metric_spec.yaml`.
- **Baseline source:** protected main branch, generated for the same eval-set SHA and full item × seed set. Do not edit reports by hand.
- **Decision:** exit 1 blocks merge. The individual submitter investigates and fixes the failure; any waiver requires instructor approval and a written reason in the PR.
- **Observed check:** `fixed` exits 0; `seeded_regression` exits 1. Its pass_rate delta is −0.271 with 95% CI [−0.500, −0.057].

## 6. Evidence gaps and risks

- [x] No real-user data; MockLLM may not represent a deployed model.
- [x] Fourteen v1 items produce wide confidence intervals and mainly detect large regressions.
- [x] Judge replay CSVs are public; no independent held-out judge calibration set is included.
- [x] Five seeds cannot reliably detect a defect occurring in only one of three runs.
- [x] Simulated cost is not a real API bill; latency is unavailable.

## 7. When to create v1.2

- Add cases from new traces or materially change labels: increment `eval_set_version`, rebuild the set and regenerate the protected baseline.
- Change metrics or thresholds for the same set: increment `metric_spec_version`, record the rationale, and keep the ratchet at least as strict as the protected spec.
- Add human or production evidence only after separate privacy and evaluation review; it is outside this lab submission.
